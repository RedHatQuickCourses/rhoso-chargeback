RHOSO Architectural Overview

This section delves into the fundamental architecture of RHOSO, outlining its core components, their interconnections, and how they collaboratively deliver robust observability and chargeback capabilities for Red Hat OpenStack Platform (RHOSP) environments. Understanding this architecture is crucial for effective deployment, configuration, and troubleshooting of RHOSO.

RHOSO is designed as a unified platform that integrates various specialized services to provide a holistic view of resource consumption and performance within RHOSP. It primarily comprises distinct yet interconnected layers for data collection, processing, storage, analysis, and presentation, catering to both real-time operational insights and historical cost allocation.

Key Architectural Layers and Components

The RHOSO architecture can be broadly categorized into several logical layers, each responsible for specific functions:

Table 1. Data Collection Layer
Component Description

RHOSP Native APIs/Agents

These are the primary sources of raw data. RHOSO leverages OpenStack’s native APIs (e.g., Nova for compute, Cinder for block storage, Neutron for networking, Glance for images, Keystone for identity) to poll for resource usage metrics, configuration changes, and tenant information. In some cases, specialized agents might be deployed on compute nodes or within OpenStack services to capture more granular or real-time metrics, logs, and traces.

Ceilometer/Gnocchi

Often, OpenStack environments already have telemetry services like Ceilometer for collecting events and meters, and Gnocchi as a time-series database for storing and querying these metrics. RHOSO might integrate with or extend these existing components to source its raw observability data.
Table 2. Data Ingestion & Processing Layer
Component Description

Data Ingestion Pipeline

This layer is responsible for receiving the raw data from the collection layer, often through message queues (e.g., Apache Kafka, RabbitMQ) for reliable and scalable ingestion. It acts as a buffer and decoupler between collectors and processors.

Data Processors/Normalizers

Once ingested, raw data streams are processed. This involves: * Normalization: Standardizing data formats from various sources. * Enrichment: Adding metadata (e.g., OpenStack project/tenant names, user IDs, resource tags) to raw metrics or logs by querying Keystone or other OpenStack services. * Filtering: Discarding irrelevant data. * Aggregation: Summarizing metrics over specific time intervals.
Table 3. Data Storage Layer
Component Description

Time-Series Database (TSDB)

Optimized for storing and querying metrics over time. This could be Prometheus, Thanos, Gnocchi, or a similar solution, providing efficient storage and retrieval for observability dashboards and chargeback calculations.

Log Storage

Dedicated storage for logs, often an ELK stack (Elasticsearch, Logstash, Kibana) or Loki, enabling efficient indexing, searching, and analysis of operational logs.

Configuration Database

A persistent store for RHOSO-specific configurations, such as chargeback rating definitions, rules, user preferences, and system settings. This is typically a relational database (e.g., PostgreSQL).
Table 4. Core Engines Layer
Component Description

Observability Engine

This engine provides the core functionalities for monitoring and diagnostics. It includes: * Metrics Query Engine: For querying the TSDB to retrieve performance and usage metrics. * Alerting Engine: Defines and triggers alerts based on predefined thresholds or patterns in metrics and logs. * Tracing/Event Management: Components for collecting and correlating distributed traces and events, providing deep insights into application and service performance.

Chargeback Engine

This is the heart of the chargeback functionality. It comprises: * Resource Usage Tracker: Continuously ingests processed resource usage data from the TSDB and other sources, mapping it to specific OpenStack projects, users, and resources. * Rating Engine: Applies the configured rating definitions and rules to the tracked resource usage data. This engine calculates the cost based on various parameters like resource type, quantity, duration, and configured price per unit. * Reporting & Billing Module: Generates detailed consumption reports, invoices, and summaries based on the calculated charges. It might also provide APIs for integration with external billing systems.
Table 5. Presentation & API Layer
Component Description

User Interface (UI)

A web-based interface for interacting with RHOSO. This typically includes: * Observability Dashboards: For visualizing metrics, logs, and traces (e.g., Grafana-based). * Chargeback Management Console: For defining rating rules, reviewing generated reports, managing tenants, and configuring chargeback settings. * Alert Management: For configuring and managing alerts.

API Gateway

Provides a unified and secure API for programmatic access to all RHOSO functionalities. This enables integration with third-party tools, automation scripts, and custom applications for data retrieval, configuration management, and report generation.

Data and Process Flow

The typical flow of data and processes within the RHOSO architecture is as follows:

  1. Data Collection: RHOSP native APIs and agents continuously collect raw telemetry data (metrics, logs, events) from various OpenStack services and underlying infrastructure.

  2. Ingestion & Processing: This raw data flows into the data ingestion pipeline, where it’s normalized, enriched with OpenStack metadata, filtered, and aggregated by the data processors.

  3. Storage: Processed metrics are stored in the Time-Series Database, logs in dedicated log storage, and RHOSO configurations in the configuration database.

  4. Observability Insights: The Observability Engine queries the TSDB and log storage to power real-time dashboards, generate alerts based on predefined rules, and provide operational insights through the UI.

  5. Chargeback Calculation: The Chargeback Engine’s Resource Usage Tracker continuously monitors resource consumption from the TSDB. The Rating Engine then applies defined rating rules to this consumption data, calculating costs per project/tenant.

  6. Reporting & Presentation: The Reporting & Billing Module generates comprehensive chargeback reports and invoices, which are then accessible via the UI or through the API.

  7. Configuration & Management: Administrators interact with the UI or API Gateway to configure chargeback rules, manage alerts, define custom dashboards, and query historical data.

Integration with RHOSP

RHOSO’s deep integration with RHOSP is fundamental to its operation. It relies on:

  • Keystone: For user authentication, authorization, and mapping resource usage to specific projects/tenants.

  • Nova, Cinder, Neutron, Glance: For collecting compute, storage, network, and image usage metrics.

  • Horizon (optional): While RHOSO provides its own UI, there might be integration points or single sign-on capabilities with the OpenStack dashboard.

This integrated approach ensures that RHOSO provides accurate and context-rich data for both operational monitoring and financial chargeback within the OpenStack environment.
